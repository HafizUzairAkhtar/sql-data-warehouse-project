# Naming Conventions

This document explains the naming standards I follow for all objects in this data warehouse — schemas, tables, views, columns, and stored procedures.

Having consistent names across the entire project makes the code easier to read, debug, and maintain. Anyone looking at this project should be able to understand what an object does just from its name.

## General Principles

These rules apply to everything in the project:

- **Format:** Use `snake_case` — all lowercase with underscores between words. No spaces, no camelCase, no PascalCase.
- **Language:** English only for all names.
- **Reserved Words:** Never use SQL reserved words (like `date`, `order`, `select`) as object names — it causes errors and confusion.

## Table Naming Conventions

The naming pattern changes depending on which layer the table belongs to.

### Bronze Layer

Bronze tables store raw data exactly as it comes from the source system. The table name must match the original source name — no renaming allowed, because we want full traceability back to the source.

**Pattern:** `<sourcesystem>_<entity>`

| Part | Description |
|------|-------------|
| `<sourcesystem>` | The name of the source system the data comes from (e.g., `crm`, `erp`) |
| `<entity>` | The original table or entity name from that source system |

**Examples:**

| Table Name | What It Means |
|------------|---------------|
| `crm_sales_details` | Sales transaction records from the CRM system |
| `crm_cust_info` | Customer information from the CRM system |
| `crm_prd_info` | Product information from the CRM system |
| `erp_cust_az12` | Customer data from the ERP system |
| `erp_loc_a101` | Location/country data from the ERP system |
| `erp_px_cat_g1v2` | Product category data from the ERP system |

---

### Silver Layer

Silver tables follow the same naming pattern as Bronze. The names stay the same — what changes is the content (cleaned, standardized data instead of raw).

**Pattern:** `<sourcesystem>_<entity>`

This consistency makes it easy to trace a silver table back to its bronze source. For example, `silver.crm_cust_info` was built from `bronze.crm_cust_info`.

---

### Gold Layer

Gold layer objects use business-friendly names that reflect what the data represents, not where it came from. These are the tables and views that analysts and stakeholders actually interact with.

**Pattern:** `<category>_<entity>`

| Part | Description |
|------|-------------|
| `<category>` | The role of the object in the data model (`dim`, `fact`, `report`) |
| `<entity>` | A clear business name describing the data (e.g., `customers`, `products`, `sales`) |

**Category Glossary:**

| Prefix | Meaning | Examples |
|--------|---------|---------|
| `dim_` | Dimension table — descriptive attributes | `dim_customers`, `dim_products` |
| `fact_` | Fact table — measurable business events | `fact_sales` |
| `report_` | Pre-aggregated reporting table | `report_sales_monthly`, `report_customers` |

**Examples:**

| Object Name | What It Represents |
|-------------|-------------------|
| `gold.dim_customers` | Enriched customer dimension combining CRM + ERP data |
| `gold.dim_products` | Product dimension with category and cost details |
| `gold.fact_sales` | Sales transactions linked to customers and products |

## Column Naming Conventions

### Surrogate Keys

Every dimension table has a surrogate key — a system-generated integer that uniquely identifies each row. These are not the original IDs from the source system.

**Pattern:** `<tablename>_key`

| Column Name | Table It Belongs To | What It Does |
|-------------|---------------------|-------------|
| `customer_key` | `dim_customers` | Unique identifier for each customer record |
| `product_key` | `dim_products` | Unique identifier for each product record |

The `_key` suffix makes it immediately obvious that this column is a surrogate key, not a natural business ID.

---

### Technical Columns

Technical columns store metadata generated by the warehouse system itself — things like when a record was loaded. These are not business data; they exist for auditing and debugging.

**Pattern:** `dwh_<column_name>`

| Column Name | What It Stores |
|-------------|---------------|
| `dwh_load_date` | The date when this record was loaded into the warehouse |

The `dwh_` prefix clearly separates system columns from business columns at a glance.

## Stored Procedures

All stored procedures used for loading data follow this pattern:

**Pattern:** `load_<layer>`

| Procedure Name | What It Does |
|----------------|-------------|
| `load_bronze` | Extracts raw data from CSV files and loads it into the Bronze layer |
| `load_silver` | Reads from Bronze, applies cleaning and transformations, loads into Silver |
| `load_gold` | Reads from Silver, applies business logic, creates Gold views |
